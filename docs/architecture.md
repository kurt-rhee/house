# Architecture decisions

## Source of truth and crate boundaries

- **core** owns semantic wall/door/window/fixture/room/dimension/layer types, stable UUIDs,
  millimeter input, schema version, and the sample constructor. No renderer types.
- **geometry** derives wall polygons, opening stations, rectangular room bounds,
  areas, dimension values, hit distances, and document validation. It uses kurbo
  for line geometry. No cached polygons replace semantic data.
- **commands** owns typed create/update/move/delete commands, atomic transactions,
  validation, snapshot history, and live document revisions.
- **io** validates before/after JSON persistence and generates standalone SVG and DXF.
- **mcp** adapts tools to typed commands and hosts the shared document actor and
  rmcp Streamable HTTP service. The actor is an application integration
  facility, not a second document engine.
- **desktop** owns ephemeral view/selection/draft-property state and egui drawing.
  It submits commands to the actor and renders immutable snapshots.

Only the worker owns a mutable Engine. GUI property drafts are proposals and
never rendered as authoritative architectural state. The HTTP service factory
creates handlers sharing the same DocumentHandle, not fresh documents. Incoming
agent requests, mouse operations, undo, open, save, and export enter one bounded
thread-safe queue. Save/export observes the document at that queue position.

## Transactions, undo, and revisions

The engine also accepts revision-checked edits. A request based on revision R
commits only if R is still current when the worker processes it. The check and
mutation run together on the owning worker, avoiding a check/commit race. GUI
object property replacement uses the draft's source revision; MCP object
editing tools expose an optional expected_revision. Conflicts change neither
the document nor either history stack. Unconditional commands remain available
for deliberate serialized edits. Revision guards are transport/command metadata;
the persisted schema is independent of these revision guards.

Each transaction clones the document, applies typed edits, then validates the
complete candidate. Any error discards it, including attached-opening changes.
Only successful validation swaps the state and pushes one undo snapshot.
Creating an object with an existing ID fails; UUIDs are never regenerated by
save/load. Delete does not silently cascade: remove referring objects in the
same transaction or validation rejects the deletion.

Undo and redo swap exact snapshots instead of applying inverse floating-point
deltas. New edits clear redo. Revision numbers increase on commits, undo, redo,
and open; undo restores semantic state exactly, excluding the revision counter.
Opening a validated project replaces the content and clears history while
preserving the live session's monotonic revision. Disk load alone retains the
stored revision. Undo history is currently unbounded and session-only.

A bounded (256-request) queue applies backpressure by rejecting a full queue.
The UI polls oneshot replies and never waits for geometry or disk I/O. The worker
publishes a new Arc<Document> only when the revision changes, under a very short RwLock and invokes
egui Context::request_repaint after processing. No lock spans a file operation
or canvas rendering. Pending GUI work remains queued if its caller disappears;
a successful command is committed before replying.

## Relationships and geometry

Wall centerlines can be arbitrary straight segments. Thickness is perpendicular
to the centerline. Door/window position is a **distance in millimeters from host
start to opening center**. Width is measured along the host; swing is a choice of
normal direction relative to start→end (left = positive normal in drawing
coordinates). Rigid translations retain opening station and width. Endpoint
updates preserve fractional station along the new wall length and retain width.
If an opening no longer fits or overlaps another opening, the whole edit fails.

Rooms explicitly name west/east/north/south walls. Their bounds use the relevant
inside wall faces, independent of wall endpoint orientation. Each referenced
wall must span the resulting rectangle. Boundary walls must remain axis aligned,
the clear width/height must be positive, and all references must exist.
Dimensions reference room IDs and width/height axes, never copied numeric text.
Area is width × height; square millimeters are converted only for display.

This rectangle-specific topology is deliberate for the first acceptance case.
Arbitrary polygons, intersection cleanup, automatically splitting room boundaries,
and general constraints would expand the milestone. Geometric contact between
unrelated walls and door swing clearance are not currently solved or validated.

## Fixtures and door types

DoorKind distinguishes Hinged and SlidingGlass while retaining the existing host,
station and width relationship. Swing is used only for hinged doors. Both types
share wall attachment, resize, overlap validation and history behavior.
The update_door MCP tool preserves kind when its optional kind argument is omitted.
Windows use the same opening fit/overlap and wall-following rules.

Baths and showers are Fixture objects with kind, layer, origin, width, depth and
clockwise rotation in degrees. They are freestanding; moving a wall does not
move them. The origin is the local top-left corner before rotation. Positive
finite sizes, bounded finite coordinates/rotation, valid IDs and layers are
validated transactionally. Plumbing, room containment, collisions and clearance
are not inferred. The symbols deliberately represent planning footprints rather
than detailed products.

Geometry derives rotated outlines, hit tests and plan symbol line segments. The
desktop, SVG and DXF consume the same plan symbols, preventing different fixture
or sliding-door shapes across interfaces. Native property drafts remain guarded
by the source revision. The MCP create_bath/create_shower/create_window/
create_sliding_glass_door/update_fixture/update_window tools dispatch the same
typed commands as the GUI. No image processing or vision inference runs inside
the server; an image-capable client can interpret a screenshot and dispatch
semantic edits after establishing scale from measured dimensions.

## Precision and deterministic behavior

The model uses f64 **millimeters**, not pixels or rounded display units. Imperial
conversion uses the rational factor 127/5 mm per inch. Display text never feeds
back into the model; a selected wall move adds the supplied delta directly.
Only explicit mouse snapping quantizes coordinates to an inch grid. Camera
transformations use f32 only on the rendering side. Undo uses exact snapshots
and JSON uses serde_json's float_roundtrip feature, preserving f64 values through
save/load. Floating-point arithmetic still has normal IEEE-754 limits; numeric
derived-geometry tests use narrow absolute tolerances rather than display text.
Endpoint equality for rectangular boundaries is exact and explicit.

Geometry is a pure function of semantic objects. BTreeMaps give deterministic
iteration/export order. UUIDs are random only at creation, then persistent.
Validation rejects nonfinite coordinates, degenerate walls, nonpositive
thickness, missing/duplicate identities and references, invalid openings, and
unsupported schema versions. Coordinates/thickness have an absolute bound of
1e9 mm to prevent pathological numeric ranges.

kurbo is used for primitive line operations. i_overlay, cavalier_contours, and
rstar are deferred: there are no polygon booleans, polyline offsets, or indexed
snapping requirements in this slice. Linear hit testing keeps five walls simple.
No custom computational-geometry algorithms or custom GPU renderer were added.
DXF export uses the dxf crate; PDF dependencies remain deferred.

## Persistence and export

Schema v2 is a human-readable serde JSON document with named semantic maps.
Loading v1 fills the empty fixtures map and default Hinged door kind, then upgrades
the version to v2 before validation. Coordinates, identities and stored revisions
are preserved. Unknown schema versions fail rather than being interpreted
optimistically. Reads validate before replacing the live document.
Save writes and syncs a unique adjacent temporary file and then renames it over
the destination; errors clean up the temporary file. This protects a prior file
from serialization/write failures, but directory fsync and crash recovery are
not implemented. Project paths are local and explicit.

SVG uses model-derived wall polygons, hosted opening cuts and door swings, room
labels/areas, and live dimension lines/values. Text is XML-escaped. Export is
independent of camera pan/zoom. Wall joins are simple overlapping rectangles;
SVG and desktop use the same semantic geometry. There is no print-scale sheet
layout or code-compliance claim.

DXF export uses dxf 0.6.2 to write AC1021 (2007) model-space entities. Both
$INSUNITS=4 and metric drawing units are set. Coordinates are (x, -y, 0), retaining
millimeters and the plan's orientation in CAD's upward-positive Y convention.
Wall intervals are split around validated door/window stations before deriving
closed LWPOLYLINE outlines, giving genuine opening gaps. Doors are LINE leaves
and ARC swings; reflection reverses the original swing's arc traversal, so start
and end angles are explicitly ordered for CAD's counterclockwise convention.
Windows add frame/glazing lines; sliding glass doors add panel lines without swing arcs.
Bath and shower symbols export as lines on source-derived FIXTURES layers. Labels use upright UTF-8 TEXT entities; control
characters become spaces so a label cannot introduce DXF group-code lines.
Dimensions are exported as LINE/tick/TEXT annotations computed from the current
room references, without claiming CAD associativity.

Source-layer names are sanitized, bounded in length, and suffixed with their full
UUID to avoid collisions. Hidden source layers omit hosted wall/door/window
geometry. Rooms and dimensions remain visible as in the desktop. Every generated
entity includes the source object UUID under registered HOUSE XData, so one wall
may tag multiple opening-separated outlines. IDs are provenance, not a DXF import
contract. DXF is an interchange snapshot; JSON remains the semantic project.
Export runs on the document worker at its queue position and reuses atomic file
replacement. It never changes document revisions or undo history.

The preferred dxf crate is sufficient for geometry serialization, but independent
ezdxf auditing exposed two writer defaults in 0.6.2: omitted symbol-table header
handles and invalid transparency value 0. Entities explicitly use opaque alpha
0x020000ff. A narrow post-serialization compatibility pass adds missing table
handles using the writer's next available handle and updates $HANDSEED; it leaves
existing handles intact and never rewrites geometry. Tests enforce unique,
nonzero handles and a seed greater than all handles. This avoids forking the
library or building a DXF geometry writer. Export timestamps/GUIDs are generated
by the library; entity geometry and ordering are deterministic, while file bytes
are not promised identical across export times.

## Local MCP lifecycle and access

The desktop automatically starts one rmcp Streamable HTTP service on
127.0.0.1:3847/mcp as part of normal app initialization, including via mise dev.
There is no on/off control or launch flag. If binding fails, the desktop remains
available and displays a persistent MCP startup error. Headless UI tests inject
an ephemeral port so parallel tests do not compete with the running application.

A random UUID bearer token is generated per app launch, required on every
HTTP request, exposed through Copy token and the launch terminal, and invalidated
when the app quits. It is a local capability, with no account or external
authentication service. rmcp validates the exact loopback Host:port and enforces
an empty Origin allowlist (rejecting every browser Origin, including null).
There is no CORS policy granting cross-origin access. MCP content is limited by
rmcp's request-body limit; this prototype assumes trusted local agents possessing
the token. There are no per-tool filesystem restrictions. Do not expose or proxy
this listener publicly.

The desktop also atomically publishes {url, token} to the local
~/Library/Application Support/House/mcp.json file. Its newly created directory
has mode 0700 and the connection file has mode 0600. Headless UI tests do not
publish this production file. On normal shutdown it is removed only if it still
contains this server's token, so a terminating old instance cannot remove a
replacement instance's connection. A stale file after a crash contains no valid
credential once its server has stopped and is overwritten by the next launch.

Codex's local http_headers_helper runs scripts/codex-mcp-headers.py to discover
the current token. User configuration contains only the endpoint and helper path.
No credential or per-user Codex configuration belongs in the repository.
The helper validates the endpoint and UUID and reports a startup instruction
when no connection file exists. Native token rotation and loopback-only access
remain unchanged.

Quitting the application revokes the token immediately, signals shutdown, and cancels active
sessions on the HTTP thread. The UI does not join that thread or wait for clients.
Dropping the HTTP runtime also cancels idle connections. The document
worker remains independently owned until its handles are dropped. Network clients await replies
asynchronously; they do not acquire the engine mutex or block the UI. No server
binary starts an unsynchronized second document. The example client connects to
the already running app and prints measurements to demonstrate this boundary.

## Validation strategy

Unit tests check typed operations and geometry; persisted snapshots are compared
by exact model equality. The bathroom integration test checks the partition's
numeric translation, each room's signed width/area delta, dimension values, door
identity/station retention, revision sequencing, rollback, and exact undo.
A real HTTP client lists and calls all eighteen tools, mixes native-style queue
requests with MCP undo, saves/loads the document, and exports SVG. DXF has an additional live HTTP move/export/undo/export test
checking numeric partition polygons and dimension values. Separate
requests exercise authorization, Host, and Origin rejection. Two independent HTTP
clients racing against the same revision must produce one commit and one conflict;
undo must then restore the original document in one step. A lifecycle test keeps
an initialized client connected during shutdown, verifies that the listener releases
its port, edits the still-live document, and restarts MCP on that same port.

Headless egui tests send actual pointer events for selection, partition dragging,
two-click wall drawing, and zoom about the pointer. They assert model coordinates
and exact undo independently of rendered pixels. A native macOS launch and the
example MCP client provide a separate integration smoke check.


DXF unit tests read the generated bytes with the Rust library and verify scale,
orientation, actual thickness, missing wall material at openings, reflected
door swing endpoints for both directions, labels, visibility, UUID provenance,
and preservation of an existing file when validation fails. A separate audit
of examples/bathroom.dxf with ezdxf 1.4.5 reported zero errors and zero fixes.
ezdxf was used only as a local verification tool and is not a runtime or test
dependency of the Rust application.
